## 3. 设计要点

- **候选集由调用方传入**，模块不自己解析 Word 包 —— 保持纯函数，也让"重绑"和"解析"两件事的失败可分开归因。
- **减少的脚注必须可见**（`NOTES_DROPPED_ON_REBIND`）。上游确实删了脚注时减少是合理的，但静默消失的脚注比标为未解决更危险。
- **展平顺序与 `assemble_package` 一致**，否则跨代比较 `notes` 会因顺序不同报假差异。

## 4. 探针抓到的真实缺陷：一条孤儿脚注变成两条（`L13-FIND-01`）

我出题：脚注存在 `footnotes.xml` 里，但**没有任何单元格引用它**，会怎样？

```
1 条孤儿脚注 -> 绑定数 2，每张表各 1 条（note_id 都是 FN-9）
```

根因在 `pipeline._note_candidates_for`：无 `target_ids` 的候选被**追加到每一张表**，
而它的 docstring 写的是"attached to the first table"。代码与自述不符。

后果不是崩溃，而是**口径错**：文档明明只有 1 个待复核条件，`stats["notes"]` 说 2，
两张表的复核包各出现一次同一条脚注。这种"数字翻倍"在验收时最容易被当成"内容更丰富"。

处置分两层：

| 层 | 动作 |
|---|---|
| 本 Loop（correction） | 无目标候选只归**首表**；文档级 `notes` 按 `note_id` 去重，去重**必须**记 `DUPLICATE_NOTE_ID_DEDUPED`，不静默 |
| 上游（pipeline） | **未修**，登记 `L13-FIND-01`，L14 处理。原因是修它要动 `pipeline.py` 与其 E2E 断言，超出 L13 白名单 |

> 我没有顺手改 pipeline：`--ff-only` 串行合并下，越过白名单改文件会让 A1 失去判定意义，
> 而这正是前面几次 RETURN 的成因。**登记比偷偷修更值钱。**
